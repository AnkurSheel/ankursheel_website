<p>Recently, I was working on a frontend feature that depended on transaction data from a Backend-For-Frontend (BFF) service. The upstream service filtered out any transaction older than X days, leaving my dataset empty and useless for development.</p>
<p>I didn't have write access to the upstream database, so seeding real data against a local database wasn't an option. And asking the upstream team to add some test data would have turned a two-hour task into a multi‑day dependency.</p>
<p>This post shows how to solve that friction inside the BFF itself using a single running example: an endpoint returning a customer’s order history by merging an <code>OrdersApi</code> and a <code>RefundsApi</code>.</p>
<h2 id="approach-1-comment-toggling">Approach 1: Comment-Toggling</h2>
<p>The quickest dirty fix is reading data from a JSON file and leaving it commented out right next to the real HTTP call.</p>
<pre><code class="language-csharp">public async Task&lt;IEnumerable&lt;OrderSummary&gt;&gt; GetOrderHistory(Guid customerId, CancellationToken ct)
{
    var orders = await _ordersApi.GetOrders(customerId, ct);
    var refunds = await _refundsApi.GetRefunds(customerId, ct);
    return Combine(orders, refunds);
 
    // Uncomment below to test locally against fixture data:
	// var orders = await LocalJsonHelper.ReadAsync&lt;OrdersResponse&gt;(&quot;./Fixtures/orders.json&quot;);
	// var refunds = await LocalJsonHelper.ReadAsync&lt;RefundsResponse&gt;(&quot;./Fixtures/refunds.json&quot;);
	// return Combine(orders, refunds);}  
</code></pre>
<p>We’ve all seen this in pull requests, and it relies entirely on developer discipline.</p>
<blockquote>
<p>This is fine for a spike</p>
</blockquote>
<p>You have to remember to revert the file before committing, and hope a reviewer catches it if you don't. Worse, that commented-out block isn't compiled, so as the surrounding method signature changes, those lines rot silently until someone tries to uncomment them and gets a wall of compiler errors instead of test data.</p>
<h2 id="approach-2-a-per-endpoint-config-check">Approach 2: A Per-Endpoint Config Check</h2>
<p>A step up is gating the data source behind a runtime flag like <code>UseLocalJsonData</code> in your <code>appsettings.json</code> and injecting it via <code>IOptions&lt;LocalDataSettings&gt;</code></p>
<pre><code class="language-csharp">public async Task&lt;IEnumerable&lt;OrderSummary&gt;&gt; GetOrderHistory(Guid customerId, CancellationToken ct)
{
    OrdersResponse orders;
	RefundsResponse refunds;

    if (_localDataSettings.UseLocalJsonData)
    {
	    orders = await LocalJsonHelper.ReadAsync&lt;OrdersResponse&gt;(&quot;./Fixtures/orders.json&quot;, ct);
	    refunds = await LocalJsonHelper.ReadAsync&lt;RefundsResponse&gt;(&quot;./Fixtures/refunds.json&quot;, ct);
	}
	else
	{
		orders = await _ordersApi.GetOrders(customerId, ct);
	    refunds = await _refundsApi.GetRefunds(customerId, ct);
	}  
    return Combine(orders, refunds);
}  
</code></pre>
<p>This is a genuine improvement. Both branches compile, and the fixture data actually flows through the real <code>Combine()</code> logic instead of sitting in a comment.</p>
<p>The problem is that your core business handlers are now littered with <code>if/else</code> branching that exists purely for local convenience. You've mixed two responsibilities into one method, added cognitive load to every code review, and introduced control paths that will never run in production.</p>
<h2 id="approach-3-push-the-switch-into-dependency-injection">Approach 3: Push the Switch into Dependency Injection</h2>
<p><img src="/assets/images/posts/clean-way-mock-upstream-apis-inside-bff-service/cover_image.png" alt="Cover Image" /></p>
<p>Instead of branching inside the handlers, we can push the switch out to the dependency injection container. The orchestrating services, mappers, and controllers stay clean. They have no idea whether the payload came from disk or over the wire.</p>
<h3 id="step-1-target-the-api-client-boundary">Step 1: Target the API Client Boundary</h3>
<p>Ensure every upstream service dependency is hidden behind an interface.</p>
<pre><code class="language-csharp">public interface IOrdersApi  
{  
    Task&lt;OrdersResponse&gt; GetOrders(Guid customerId, CancellationToken ct);}  
</code></pre>
<h3 id="step-2-implement-the-local-client">Step 2: Implement the Local Client</h3>
<p>Implement a local version of the client that reads raw upstream JSON payloads from disk.</p>
<pre><code class="language-csharp">public class LocalOrdersApi : IOrdersApi  
{  
    public async Task&lt;OrdersResponse&gt; GetOrders(Guid customerId, CancellationToken ct)
	{
		return await LocalJsonHelper.ReadAsync&lt;OrdersResponse&gt;(&quot;./Fixtures/RawUpstream/orders.json&quot;, ct);
	} 
 }
</code></pre>
<h3 id="step-3-conditionally-register-in-the-di-container">Step 3: Conditionally Register in the DI Container</h3>
<p>Register your production HTTP clients by default, then conditionally overwrite them in development.</p>
<pre><code class="language-csharp">// 1. Register the real API clients
services.AddScoped&lt;IOrdersApi, OrdersApi&gt;();
services.AddScoped&lt;IRefundsApi, RefundsApi&gt;();
  
// 2. Conditionally overwrite them for local development
if (ShouldUseLocalData(environment, configuration))
{
	services.AddScoped&lt;IOrdersApi, LocalOrdersApi&gt;();
	services.AddScoped&lt;IRefundsApi, LocalRefundsApi&gt;();
}  
</code></pre>
<p><strong>What are we doing here?</strong> The registration order matters. ASP.NET Core's container resolves the last registration for a given interface, so the local clients silently take over without either registration knowing the other exists. Nothing in <code>OrderHistoryService</code> or its callers changes at all.</p>
<p>Notice the check is <code>ShouldUseLocalData(environment, configuration)</code> rather than a bare config lookup. That's deliberate. It adds an independent environment check on top of the config flag, so even if someone misconfigures <code>appsettings.json</code> in a shared environment, fixture data still can't leak into production.</p>
<pre><code class="language-csharp">private bool ShouldUseLocalData(IWebHostEnvironment environment, IConfiguration configuration)
{
	var localDataSettings = configuration.GetSection(LocalDataSettings.SectionName).Get&lt;LocalDataSettings&gt;();
	return localDataSettings.UseLocalJsonData &amp;&amp; environment.IsDevelopment();
}  
</code></pre>
<h3 id="step-4-isolate-local-code-from-production-assemblies">Step 4: Isolate Local Code from Production Assemblies</h3>
<p>If you want absolute isolation, move the <code>Local*Api</code> classes into a separate project, <code>Bff.LocalDevelopment</code>, and reference it conditionally</p>
<pre><code class="language-xml">&lt;ItemGroup Condition=&quot;'$(IncludeLocalDevelopmentAssembly)' == 'true'&quot;&gt;  
  &lt;ProjectReference Include=&quot;..\Bff.LocalDevelopment\Bff.LocalDevelopment.csproj&quot; /&gt;&lt;/ItemGroup&gt;  
</code></pre>
<p>You can pass <code>IncludeLocalDevelopmentAssembly</code> via <code>-p</code> on the command line, but a more durable option is setting it in <code>Directory.Build.props</code> and forcing it off on CI agents:</p>
<pre><code class="language-xml">&lt;Project&gt;
  &lt;PropertyGroup&gt;
    &lt;IncludeLocalDevelopmentAssembly Condition=&quot;'$(IncludeLocalDevelopmentAssembly)' == ''&quot;&gt;true&lt;/IncludeLocalDevelopmentAssembly&gt;
  &lt;/PropertyGroup&gt;

  &lt;!-- Force false on CI build agents --&gt;
  &lt;PropertyGroup Condition=&quot;'$(GITHUB_ACTIONS)' == 'true'&quot;&gt;
    &lt;IncludeLocalDevelopmentAssembly&gt;false&lt;/IncludeLocalDevelopmentAssembly&gt;
  &lt;/PropertyGroup&gt;
&lt;/Project&gt;
</code></pre>
<p>The first <code>PropertyGroup</code> defaults the property to <code>true</code> only if nothing has set it already, so a plain local build gets the assembly with no extra flags needed. The second <code>PropertyGroup</code> only matches on GitHub Actions runners, which set <code>$(GITHUB_ACTIONS)</code> to <code>true</code> automatically, and forces the value back to <code>false</code> there. Nobody on the team has to remember to opt out locally, and CI can't opt in by accident.</p>
<p><strong>Why not just check <code>$(Configuration) == 'Debug'</code>?</strong> Build configuration and runtime environment are different concepts. It's far too easy for a developer to run <code>dotnet build -c Release</code> locally, or for a pipeline step to compile in Debug mode on a wrong assumption. An explicit MSBuild property removes that guesswork.</p>
<h3 id="is-this-overengineering">Is This Overengineering?</h3>
<p>Fair question. That's four steps, an interface per client, a <code>ShouldUseLocalData</code> guard, and possibly a whole separate assembly for what's ultimately a way to read a JSON file instead of calling an API.</p>
<p>If you need this for a single one-off bug, it probably is overkill. Approach 1's commented-out block is faster to write, and you'll delete it in twenty minutes anyway.</p>
<p>It stops being overengineering the moment the local codepath needs to be kept for a longer time, which in my experience happens quickly. The interface boundary that lets you swap in fixture data is the same boundary you'd want for testing your code, so you're not adding an abstraction so much as formalising a seam that probably should have existed already. Once that's in place, Steps 3 and 4 are a few lines of DI registration and an MSBuild condition, not a new layer to maintain.</p>
<p>However, if you're only doing this for a handful of endpoints, Step 4 is probably overkill and you can skip it.</p>
<h2 id="what-this-unlocks">What This Unlocks</h2>
<h3 id="unlock-1-preventing-drift-with-snapshot-testing">Unlock 1: Preventing Drift with Snapshot Testing</h3>
<p>Because a fixture-backed client is deterministic, you can run it through your production <code>OrderHistoryService</code> in a unit test and assert the output with a snapshot tool.</p>
<pre><code class="language-csharp">[Fact]
public async Task GetOrderHistory_MatchesSnapshot()
{
    var localOrdersApi = new LocalOrdersApi(Options.Create(new LocalDataSettings()));
    var service = new OrderHistoryService(localOrdersApi, new OrderMapper());

    var result = await service.GetOrderHistory(Guid.Empty, CancellationToken.None);

    await Verify(result);
}
</code></pre>
<p>If someone renames a property or breaks a mapping rule, the snapshot test fails instantly in CI with a visual diff and helps you catch breaking changes much faster.</p>
<h3 id="unlock-2-automating-frontend-mocks">Unlock 2: Automating Frontend Mocks</h3>
<p>Instead of frontend teams maintaining separate hand-written stubs that drift over time, you can pipe your verified <code>.verified.json</code> snapshots directly into WireMock stubs, Storybook fixtures, or TypeScript type generators. Your frontend mocks are now guaranteed to match true backend execution output.</p>
<h3 id="unlock-3-simulating-upstream-failures-and-edge-cases">Unlock 3: Simulating Upstream Failures and Edge Cases</h3>
<p>Happy-path testing is straightforward, but add a failure flag to the local client and you can simulate an upstream outage without touching the network at all.</p>
<pre><code class="language-csharp">public class LocalOrdersApi : IOrdersApi
{
    private readonly LocalDataSettings _settings;

    public LocalOrdersApi(IOptions&lt;LocalDataSettings&gt; settings)
    {
        _settings = settings.Value;
    }

    public async Task&lt;OrdersResponse&gt; GetOrders(Guid customerId, CancellationToken ct)
    {
        if (_settings.SimulateOrdersApiError)
        {
            throw new HttpRequestException(&quot;Simulated upstream 503 Service Unavailable&quot;);
        }

        return await LocalJsonHelper.ReadAsync&lt;OrdersResponse&gt;(&quot;./Fixtures/RawUpstream/orders.json&quot;, ct);
    }
}
</code></pre>
<p>Toggle <code>&quot;SimulateOrdersApiError&quot;: true</code> locally to check your fallback and retry logic actually does what you think it does.</p>
<h2 id="summary">Summary</h2>
<p>The extra interface and DI wiring cost a little upfront, but you get deterministic data for local devving. The edge case you couldn't get an upstream service to return becomes a JSON file away.</p>
